## 背景佇列實測

`tools/live_queue_check.py` 使用真實模型及背景子程序，先加入 A、B、C，在 A 未完成時加入 D，並同時啟動兩個 worker 驗證排他性。每份文件都驗證 `indexed` 事件早於 `completed`，處理順序為 A → B → C → D，通知確認後不再重播。

為減少逐檔重載模型，背景程序在等待圖譜時釋放工作鎖但保留模型；等待助手超過 120 秒則退出，佇列仍持久保存。最終實測四份文件共約 59.72 秒，其中第一份的冷啟動及索引約 58.56 秒，後三份沿用模型。測試文件刻意沒有領域關係，因此圖譜提交為空，這段時間不能代表真實助手圖譜抽取耗時。事件記錄見 `live-queue.json`。

## 尚未完成的驗收與限制

- **兩個助手的真實聊天附件、skill 發現與使用者可見通知**：目前沒有使用者透過聊天畫面上傳的文件，也沒有完成 Claude Code 桌面版的互動操作。安裝器及附件協定測試不能替代這項驗收。
- **完整一千份／一萬頁資料集**：目前以小型真實模型測試與大型合成向量測試分別驗證，尚未跑完整規模的解析與圖譜抽取。
- **跨平台及 Python 3.11**：未實測，不宣稱已正式驗收。
- 通知是助手持續輪詢後回覆，不是原生推播。訊息發出與本機 ack 之間沒有跨系統交易；中斷於兩者之間可能重播一次，skill 要求恢復時比對對話。
- 圖譜的來源片段可由程式驗證，關係的語意正確性仍取決於助手。只用確切名稱／類型識別實體，不宣稱完整實體消歧義。

建議正式 UI 驗收使用安裝包附的四份 `examples` 文件：在每個助手的新本機對話執行 setup，上傳 A/B/C 後明確 add，A 未完成時再上傳並 add D；逐檔檢查通知、詢問可回答及無答案問題，再刪除一份並確認不再被檢索。此項需要實際宿主與附件，不可用偽造 manifest 宣稱通過。
